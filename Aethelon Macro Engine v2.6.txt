       AETHELON MACRO ENGINE - ARCHITECTURE ROADMAP (v2.6)
              [Execution-Ordered Institutional Edition]
================================================================================

Document role
-------------
v2.6 keeps the same product destination as v2.5.
It improves stage order, proof gates, and observability so the core is
proven before heavy product clothing is added.

Philosophy
----------
1. Build the brain and data path.
2. Prove they work under real use.
3. Make results visible in the GUI early.
4. Then add execution bridges, chart overlays, polish, and long-horizon work.
5. Optimize for clarity and reliability first; language rewrites only when needed.

--------------------------------------------------------------------------------
GLOBAL RULES
--------------------------------------------------------------------------------
• Source of product intent remains the Aethelon vision (macro engine for discretionary trading support).
• Technical analysis stays with the trader; the engine focuses on fundamentals and decision support.
• Every major stage needs a Definition of Done.
• Long live tests (30+ minutes) are run by the project owner on a local machine.
• Short code/smoke tests may be run by the coding agent.
• Prefer soft connection and gradual migration over rewriting news_engine.py in one shot.
• Do not advance into heavy visuals/execution until Prove Gate passes.

--------------------------------------------------------------------------------
STAGE DETAILS
--------------------------------------------------------------------------------

STAGE A — Core & Data Contracts
Goal:
  Stable app paths, centralized logging, and strict data contracts.
Done when:
  AppData paths work, logger rotates, Pydantic contracts exist, basic log verification is possible.

STAGE B — Resilient Async Ingestion
Goal:
  Reliable async ingestion decoupled from NLP/storage side effects.
Done when:
  Drivers + orchestrator work, retries exist, secrets are not hardcoded, dual/legacy safety is acceptable.

STAGE C — Causal Macro Brain
Goal:
  Offline macro reasoning:
  - 4 regimes: Reflation, Stagflation, Goldilocks, Deflation
  - Hard invalidation
  - Soft divergence
  - Exogenous shock isolation
Done when:
  Brain modules exist, offline tests pass, no GUI dependency required.

STAGE C+ — Analysis Output Contract
Goal:
  One stable package the rest of the system can consume.
Includes:
  - AnalysisPackage
  - status: CALM / WATCH / ALERT / SHOCK
  - offline package tests / brain day-flow checks
Done when:
  assemble_analysis_package is stable and documented as the output contract.

STAGE D — 3-Layer Storage
Goal:
  - L1 Hot Cache (RAM, live snapshots)
  - L2 Warm Store (SQLite WAL, recent history)
  - L3 Cold Vault (compressed/long-term archive start)
Done when:
  Storage APIs exist, offline storage tests pass, user data is not wiped.

STAGE P — Prove Gate (Live Core)
Goal:
  Prove the core path before dressing the product.
Minimum proof:
  - live listener path runs
  - ingestion produces usable context
  - AnalysisPackage can be assembled from near-real context
  - central logs are healthy
  - no crash over an owner-run real window (for example 30–60 minutes)
Note:
  Agent may prepare scripts/checks. Owner runs long live tests locally.

STAGE E — Desk Visibility (GUI Panel)
Goal:
  Make the system observable early in a real panel.
Owner should see:
  - regime
  - consumer status
  - hard/soft/shock summary
  - basic ingestion/storage health
Rules:
  Thin GUI connection only. No full chart-overlay suite yet.
  Existing GUI must not be broken.
Done when:
  Owner can inspect core outputs in-app during real tests.

STAGE F — Execution, IPC & Chart Overlays
Goal:
  Same destination as old Stage E:
  - MT5 via socket IPC (ZeroMQ / gRPC / WebSockets)
  - TradingView local API / lightweight charts path
  - 5 overlays:
    1) Smart Event Pins
    2) Macro Bias Ribbon
    3) Fundamental Divergence Overlay
    4) Pre-Event Playbook Zones
    5) Fundamental Signal Filtering
Rule:
  Enter only after Stage E visibility and Prove Gate are solid.

STAGE G — Process Isolation & Async Shell
Goal:
  Keep UI responsive under load.
Includes:
  dedicated UI thread, background workers for heavy I/O and analysis, zero-freeze behavior.

STAGE H — Audit, Polish & Optimization
Goal:
  Product maturity, not mandatory language rewrite.
Includes:
  - offline intermediary AI audit of system judgments
  - professional UI polish
  - Persian/English presentation where planned
  - endurance testing before v1.0.0
  - code efficiency cleanup
  - optional Go/Rust/C++ only if Python becomes a proven bottleneck

--------------------------------------------------------------------------------
WHY THIS ORDER
--------------------------------------------------------------------------------
v2.5 jumped toward execution/visual clothing while core observability was still late.
v2.6 forces:
  brain → package → storage → prove live → see in GUI → then IPC/overlays → then hard shell/polish.
